# RBAC и области доступа

Статус: backend реализован. Отдельный администратор, иерархия территорий и
правило доступа техника согласованы с пользователем.

## Цель и границы

Расширить существующие роли и разрешения ограничением доступа к объектам,
каналам и связанным данным. Первый этап: модели, миграция с начальными ролями
и разрешениями, backend-проверки области доступа, API назначения доступа и тесты.
Перечисленные в требованиях дашборды, прогнозы, заявки и отчёты определяют
каталог разрешений; реализация этих предметных модулей — отдельные этапы.

## Правила доступа

- Администратор остаётся отдельной глобальной ролью `admin`.
- Подразделение содержит районы; район относится к одному подразделению.
- Объект относится к одному району. Существующие объекты могут временно не
  иметь района: это не даёт доступа обычным пользователям.
- Техник видит пересечение своих районов и явно назначенных ему объектов.
- Диспетчер видит объекты назначенных районов и явно назначенные объекты.
- Руководитель видит объекты назначенных подразделений.
- Канал наследует область доступа объекта; событие — канала.
- Каналы без объекта доступны только администратору.
- Назначение родительского объекта не открывает потомков автоматически.
- Отсутствие назначений означает отсутствие доступа, кроме администратора.

## Модели и связи

Сохраняем `roles`, `permissions`, `user_roles`, `role_permissions`.

| Изменение | Назначение |
|---|---|
| `divisions` | Подразделения: идентификатор, уникальный код, название |
| `districts` | Районы: идентификатор, уникальный код, название, `division_id` |
| `objects.district_id` | Внешний ключ на район, индекс; nullable для существующих данных |
| `user_role_divisions` | Назначения подразделений пользователю в конкретной роли |
| `user_role_districts` | Назначения районов пользователю в конкретной роли |
| `user_role_objects` | Назначения отдельных объектов пользователю в конкретной роли |

Каждая таблица назначений содержит `user_id`, `role_id` и идентификатор ресурса.
Составной внешний ключ `(user_id, role_id)` ссылается на `user_roles` с
каскадным удалением; составной первичный ключ исключает повторные назначения.
Удаление района/подразделения с зависимыми объектами/районами запрещено.
Новые справочники используют строковые UUID, как существующие справочники;
идентификаторы объектов и каналов сохраняются без изменений.

Область привязана к роли, чтобы права разных ролей не перемножались:
если пользователь — руководитель подразделения А и техник объекта Б,
права руководителя не распространяются на Б.
Для каждой операции выбираются роли с нужным разрешением и объединяются
только области этих ролей. Глобальные административные права отдельно.

## Матрица ролей

| Роль | Просмотр | Действия |
|---|---|---|
| `dispatcher` / Диспетчер | Аналитический дашборд, карта, объекты/каналы, прогнозы, риски, предупреждения и уведомления | Верификация прогноза, фиксация решения |
| `technician` / Техник | Свои объекты/каналы, карта, назначенные заявки, карточки оборудования, история неисправностей, рекомендации | Принять назначенную заявку, изменить статус, записать результат проверки/ремонта, комментарий |
| `manager` / Руководитель | Сводный дашборд, карта подразделения, объекты/каналы, риски/инциденты, заявки и результаты, история ремонтов | Экспорт отчётов PDF/XLSX |
| `admin` / Администратор | Вся система, журнал действий и системные параметры | Пользователи, роли, назначения областей доступа, справочники объектов/каналов |

Разрешения именуются `resource.action`, например `object.view`, `channel.view`,
`forecast.verify`, `forecast.decide`, `ticket.accept`, `ticket.update_status`,
`ticket.record_result`, `ticket.comment`, `report.export_pdf`, `report.export_xlsx`,
`access.manage`, `audit.view`, `settings.view`. Для различающихся дашбордов
предусматриваются отдельные разрешения. Существующие разрешения сохраняются.

Роль `user` сохраняется для совместимости с регистрацией, но не получает
предметного доступа. Рабочие роли и назначения выдаёт администратор.
Начальные данные добавляются миграцией без перезаписи существующих назначений.
Миграция дополняет разрешения штатных ролей согласно матрице, сохраняя их
существующие идентификаторы, названия и дополнительные разрешения.
Пользовательские роли сохраняют прежний механизм разрешений, но предметные
области пока поддерживаются только для `dispatcher`, `technician`, `manager`.

## Реализация и проверка

Стек: существующие SQLAlchemy 2, PostgreSQL, Alembic, FastAPI и Pydantic.
Модели размещаются в `app/dbapi/models`, схемы в `app/schemas`, API назначений
в `app/api`, общая политика доступа — в отдельном backend-модуле.
Стиль: типизированные `Mapped`-поля и функции, async-сессии, snake_case:

```python
district_id: Mapped[str | None] = mapped_column(
    String(36), ForeignKey("districts.id"), nullable=True, index=True
)
```

Порядок: модели/миграция → начальные роли/права → фильтры и проверки → API
назначений → интеграция с существующим управлением ролями → тесты.
Замена ролей должна сохранять назначения неизменённых ролей: текущее удаление
всех `user_roles` перед повторной вставкой для новых каскадных связей не подходит.

Проверка списков выполняется SQL-фильтром до подсчёта количества и пагинации;
доступ по идентификатору проверяется той же политикой. Для будущих заявок
дополнительно обязателен контроль исполнителя, одной области объекта недостаточно.

Тесты pytest в `tests/`: разрешённый/запрещённый доступ каждой роли,
отсутствие назначений, несколько ролей без расширения чужих полномочий,
каналы без объекта, сохранение назначений при обновлении ролей,
недопустимые ссылки и отсутствие права управлять назначениями.
SQL-фильтры и миграции проверяются на отдельной тестовой PostgreSQL БД.

Команды: `uv run pytest`; `uv run alembic upgrade head` — только для явно
выбранной тестовой БД при проверке миграции; `uv run uvicorn main:app --reload --port 8000`.

Всегда: сохранять существующие данные, проверять права на backend, тестировать
отрицательные сценарии. Не применять миграции к рабочей БД автоматически,
не назначать рабочие роли при публичной регистрации, не менять секреты.

## API и порядок настройки

Все пути приведены с стандартным префиксом `/api`. Административные запросы
ниже требуют `access.manage`; смена ролей — существующего `user.edit`.
JWT передаётся в `Authorization: Bearer ...`.

1. Применить миграцию: `uv run alembic upgrade head`.
2. Зарегистрировать пользователя и назначить первого администратора:
   `uv run python scripts/promote_user.py admin@example.com`.
3. Создать подразделение: `POST /api/admin/divisions`, тело
   `{"code": "north", "name": "Северное подразделение"}`.
4. Создать район: `POST /api/admin/districts`, тело
   `{"code": "district-1", "name": "Район 1", "division_id": "UUID подразделения"}`.
5. Привязать существующий объект к району:
   `PUT /api/admin/objects/123/district`, тело `{"district_id": "UUID района"}`.
6. Назначить пользователю роли через существующий
   `PUT /api/admin/users/{user_id}/roles` с `{"role_ids": ["UUID роли"]}`.
7. Назначить область роли:
   `PUT /api/admin/users/{user_id}/roles/{role_id}/scope`.

Примеры тела последнего запроса:

```json
{"district_ids": ["UUID района"], "object_ids": [123, 124]}
```

Техник получает только перечисленные объекты в перечисленных районах.
Для диспетчера это все объекты перечисленных районов плюс отдельные объекты.
Руководителю передаётся `{"division_ids": ["UUID подразделения"]}`.
PUT полностью заменяет область одной роли, `{}` очищает её. Неподходящие
роли поля, неизвестные ресурсы и объекты техника вне его районов отклоняются.
`role_id` в URL — идентификатор роли, а не её код.

Просмотр назначений: `GET` того же `/scope`.
Списки справочников: `GET /api/admin/divisions`, `GET /api/admin/districts`.
Объекты: `GET /api/objects`, `GET /api/objects/{id}`.
Каналы: `GET /api/channels?object_id=123`, `GET /api/channels/{id}`.
Списки объектов и каналов поддерживают `page` и `page_size` (до 100), возвращают
`items`, `total`, `page`, `page_size`; `total` учитывает область доступа.
Чужой или отсутствующий объект/канал возвращает 404, отсутствие разрешения — 403.

## Использование в будущих модулях

`app/rbac.py` предоставляет `accessible_objects`, `accessible_channels`,
`accessible_events` и `object_access_condition`. В запрос передаётся разрешение
именно выполняемого действия. Например, для верификации прогноза фильтровать
его объект через `object_access_condition(user.id, "forecast.verify")`.
Нельзя отдельно объединить все права пользователя и все его территории:
это расширит права пользователя с несколькими ролями.

`/api/me` уже возвращает `role_codes` и `permission_codes` для интерфейса.
Новые предметные страницы и UI назначения территорий ещё не реализованы;
подготовленные права сами по себе не создают функциональность прогнозов,
заявок, аудита или экспорта. Назначения сейчас доступны через API и `/docs`.

## Проверки и откат

Для интеграционных тестов указать отдельную PostgreSQL БД:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://test_user:test_password@localhost:5432/mk_sensors_test uv run pytest
```

Тесты создают уникальную схему внутри транзакции и откатывают её после каждого
сценария. Без `TEST_DATABASE_URL` тесты PostgreSQL пропускаются, остальные идут
обычным способом. Проверено 32 теста с PostgreSQL, миграции с нуля,
`alembic check`, откат новой миграции и её повторное применение.

Откат до `75c03db184ee` удаляет территории и назначения доступа, но сохраняет
роли/разрешения и их связи, чтобы не удалить уже используемые учётные данные.
Повторное применение не дублирует роли, разрешения и связи.
